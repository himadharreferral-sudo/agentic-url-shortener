# Agentic Software Engineering System — URL Shortener

A runnable prototype demonstrating an **agentic SDLC orchestration layer** paired with a **production-style URL Shortener service** (`POST /api/v1/links`, `GET /{code}`, `GET /api/v1/links/{code}/stats`, `GET /health`), security/reliability guardrails, and full unit/integration tests using only the Python standard library.

## Quick Setup & Execution

1. Ensure **Python 3.10+** is installed.
2. Run the test suite from the project root (`agentic-url-shortener/`):
   ```bash
   python -m unittest discover -s tests -v
   ```
3. Start the URL Shortener server:
   ```bash
   python -m src.app
   ```

4. Open the live SRE dashboard at `http://127.0.0.1:8080/dashboard`. It summarizes traffic, 5xx errors, response-time percentiles, in-flight requests, thread count, and LRU cache utilization over a rolling one-hour window.
   The metrics are process-local and reset when the server restarts. A dashboard screenshot is saved at [docs/metrics-dashboard.png](docs/metrics-dashboard.png).
5. Check liveness, readiness, and raw SRE-style metrics:
   - `GET /health`: process liveness and circuit-breaker state.
   - `GET /ready`: verifies SQLite is reachable; returns `503` when it is not.
   - `GET /metrics`: Prometheus text-format request counters, latency histograms, startup duration, and example SLO targets.
   - `GET /api/v1/observability`: JSON snapshot consumed by the dashboard.

6. Run the deterministic orchestration scenarios:
   ```bash
   python -m orchestrator
   ```
   The greenfield scenario asks for explicit release approval; without an approval callback, high-impact work is denied. To persist append-only JSONL audit events, pass `--audit-dir orchestrator-audit`.

## Container Deployment

Build and run the service image from the project root:

```bash
docker build -t agentic-url-shortener:local .
docker run --name url-shortener --rm -p 8080:8080 \
  -v shortener-data:/data \
  -e PUBLIC_BASE_URL=http://localhost:8080 \
  agentic-url-shortener:local
```

The image runs as a non-root user, binds to `0.0.0.0:8080`, stores SQLite data at
`/data/shortener.db`, and has a Docker health check against `/ready`. Set
`PUBLIC_BASE_URL` to the externally reachable HTTPS URL when deploying behind an
ingress or reverse proxy. Orchestrators can use `/health` for liveness and `/ready`
for readiness. The process runs as UID/GID `10001`; configure persistent-volume
permissions accordingly (for Kubernetes, `fsGroup: 10001` is commonly appropriate).

This SQLite prototype should run as a **single replica with persistent storage**.
Its database, cache, rate limiter, circuit breaker, and metrics are not designed for
multi-replica sharing. Use a shared database/cache and external metrics backend
before scaling horizontally.

## Google Cloud Run with Terraform

Terraform configuration is in `infra/terraform/`. It provisions the Artifact
Registry repository, a least-privilege runtime service account, and a public
Cloud Run service in `us-central1` by default. The service is capped at one
instance with request concurrency set to one.

> **Demo limitation:** Cloud Run uses `/tmp/shortener.db`, which is ephemeral.
> SQLite data can be lost when an instance is replaced or the service is
> redeployed. The one-instance cap does not make this durable. Do not use this
> setup for production data; migrate storage to a managed database such as
> Cloud SQL for PostgreSQL first. The public service also has no application
> authentication, so anyone can create and resolve links.

Prerequisites: Terraform 1.5+, Docker, and the Google Cloud CLI (`gcloud`).
Authenticate to the target project, then prepare the Terraform variables:

```powershell
gcloud auth login
gcloud auth application-default login
gcloud config set project YOUR_PROJECT_ID
Set-Location .\infra\terraform
Copy-Item .\terraform.tfvars.example .\terraform.tfvars
# Edit terraform.tfvars and set project_id to YOUR_PROJECT_ID.
terraform init
```

Create the Artifact Registry repository first. The temporary hello-world image
is used only to satisfy the required image variable during this targeted
bootstrap; it does not deploy the Cloud Run service:

```powershell
terraform apply -target=google_artifact_registry_repository.images `
  -var="image=us-docker.pkg.dev/cloudrun/container/hello"
```

Build and push this project image, then apply the full infrastructure:

```powershell
$projectId = "YOUR_PROJECT_ID"
$image = "us-central1-docker.pkg.dev/$projectId/url-shortener/url-shortener:v1"
gcloud auth configure-docker us-central1-docker.pkg.dev
Set-Location ..\..
docker build -t $image .
docker push $image
Set-Location .\infra\terraform
terraform apply -var="image=$image"
```

The service URL is generated by Cloud Run, so set it as the public short-link
base URL in a second apply:

```powershell
$serviceUrl = terraform output -raw service_url
terraform apply -var="image=$image" -var="public_base_url=$serviceUrl"
Write-Output $serviceUrl
```

Open `$serviceUrl/dashboard`. The initial apply does not set a valid public
short-link base URL; complete the second apply before creating links. Terraform
state and `terraform.tfvars` are local and ignored by `infra/terraform/.gitignore`;
store state remotely with locking before collaborating or using this beyond a
demo. Run `terraform destroy -var="image=$image" -var="public_base_url=$serviceUrl"`
from `infra/terraform` to remove the provisioned resources.

## Limitations & Trade-Offs
- Uses SQLite and an in-memory fallback cache/rate-limiter suitable for single-node prototyping; multi-node production deployments should swap in distributed Redis/PostgreSQL and external secret/IAM scanners.
- Human approval checkpoints are modeled via a synchronous callback hook rather than an asynchronous ticketing/webhook workflow.
- Scenario task runners are deterministic stand-ins, not live LLM agents; the engine is ready for injected runners, but agent-provider/tool integration and code-generation execution are outside this prototype.
- JSONL audit output is optional and append-only, but is not tamper-evident or centrally managed. The in-memory orchestration state and metrics reset on restart.
- SRE metrics are process-local and reset on restart; configure Prometheus or an equivalent collector to retain time series. The exported 99.9% availability and 100 ms redirect P95 objectives are interview/demo examples, not measured guarantees or production SLOs.
- The dashboard's saturation indicators are in-flight requests, active threads, and LRU occupancy; it does not measure CPU/memory or enforce a bounded worker pool.
- The API has no authentication. It limits request bodies and keys its in-memory rate limiter by peer IP, but a production deployment behind a proxy needs trusted client-IP handling and authenticated tenant identity. Redirecting to arbitrary public URLs is intentional; apply an allowlist/abuse controls if that is not acceptable for the product.
